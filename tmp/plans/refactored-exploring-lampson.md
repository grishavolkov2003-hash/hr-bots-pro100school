# План: полный проход по 10 аспектам "идеально работающего проекта" (hr-bot + brosky-bot)

## Контекст

После вчерашней чистки мёртвого кода (подсистема слотов/календаря) и сегодняшнего code-review силами двух независимых субагентов Шеф спросил, какие вообще аспекты бывают у идеально работающего проекта. Получив список из 10 пунктов (корректность, обработка отказов, конкурентность, наблюдаемость, согласованность данных, тесты, безопасность, отсутствие мёртвого кода, деплой/откат, документация), Шеф явно попросил: **пройтись по всем 10 до идеала**, не экономя на объёме — задействовав планировщика, критика и research-агентов.

Собрано двумя Explore-агентами (наблюдаемость/деплой и безопасность/документация) плюс верификацией руками (grep/read реального кода) — все факты ниже подтверждены чтением кода, не гипотезы. План прошёл через Plan-агента, затем через агента-критика, часть находок критика учтена (ниже помечено **[критика]**).

**Найдена новая проблема при разведке (не была в исходном ревью):** `CREDS_PATTERN` в обоих ботах ловит логин/пароль от аккаунта profi.ru, который кандидат присылает в чат при получении доступа, и кладёт открытым текстом в 3 места: историю переписки в SQLite (`add_message` вызывается ДО проверки паттерна — `hr-bot/main.py:300` до `:315`), ячейку Google Sheets (`main.py:325`), и личку коллеге `mx_mish` (`main.py:336`). Шеф решил: убрать из первых двух мест, пересылку коллеге оставить (без неё некому выдавать аккаунт).

## Как выполняется (установившийся в этой сессии паттерн, не пересматривается)

Каждая задача — отдельный маленький PR: правка → критика плана правки (для нетривиальных) → `py_compile` → `pytest` (локально/на сервере) → деплой ОДНОГО файла/бота → `journalctl` без ошибок → следующая задача. Не смешивать правки из разных ботов или разных задач в одном деплое. После каждой задачи — короткий доклад Шефу, не молчаливое продолжение.

### Phase B — устойчивость и наблюдаемость (после T1; **[критика]** объединено в меньшее число деплоев, чем в черновике)

**T4. FloodWaitError + переход на `logging`** — один комбинированный проход на файл, не два отдельных (иначе дважды правим одни и те же функции handler/decision_loop/patrol)
- `telethon.errors.FloodWaitError` — обернуть `send_message`/`send_file` в hot-path обоих ботов, `await asyncio.sleep(e.seconds)` + один повтор.
- `print(...)` → модуль `logging`. **[критика, важно]:** НЕ заводить `RotatingFileHandler`/отдельный файл логов — systemd/journald уже перехватывает stdout каждого юнита со своей ротацией (`journalctl -u hr-bot`), второе хранилище логов на диске для проекта с одним владельцем — лишняя сущность без пользы. Используем `StreamHandler` в stdout, чтобы journald остался единственным источником, но с уровнями (debug/info/warning/error) вместо голого print.
- Заодно закрываем "тихие" `except Exception: pass` без единого print (`hr-bot/main.py:333-334,1049-1050,1223-1224`) — минимум `logging.warning(...)`.
- Алерт на сбой самого `send_signal()` — тоже через `logging.error`, без отдельного `alerts_failed.log` (**[критика]**: то же самое обоснование, второй файл никто не будет читать отдельно от journalctl).

**T5. Тот же переход на `logging` в `manager_bot.py`** — отдельная задача/деплой, другой сервис (`hr-manager-bot.service`), ниже срочность.

### Phase E — деплой и откат

**T10 (рекомендация планировщика, не прямой запрос Шефа — отметить явно перед стартом).** Лёгкий CI: `.github/workflows/tests.yml`, прогон 39 pytest на push/PR по обеим поддиректориям. Не трогает ручной деплой на VPS, чисто страховка от регрессий до того как правки уйдут на сервер руками.

**T11. Rollback — ПЕРЕСМОТРЕН по итогам критики.** Черновик плана предлагал release-каталоги (`/opt/hr-bot-releases/<ts>/` + симлинк) — критик указал на реальный риск: `/opt/hr-bot` и `/opt/brosky-bot` уже участвуют в существующей cross-bot symlink-схеме (`storage.py`/`llm.py`/`sheets.py`/`folders.py`/`venv`/`.env`/`google_creds.json`/`candidates.db` расшарены абсолютными путями между директориями), и подмена `/opt/hr-bot` на симлинк рискует `FileNotFoundError` на живых кандидатах при первом же переключении, без стейджинга для обкатки. **Выбран более безопасный подход, не трогающий структуру директорий**: формализовать в скрипт то, что этой сессией уже делалось вручную (бэкап перед каждым деплоем) —
- `scripts/deploy.sh <bot>`: копирует текущие файлы в `/root/deploy_backups/<bot>/<timestamp>/` перед копированием новых, затем `systemctl restart`.
- `scripts/rollback.sh <bot> [timestamp|latest]`: копирует файлы из указанного (или последнего) бэкапа обратно, `systemctl restart`.
- Задокументировать в README, **протестировать один раз вживую** на VPS в тихое окно (не во время активной переписки с кандидатами) — задеплоить заведомо тривиальное изменение, откатить, убедиться что сервис поднялся с прежним поведением.
